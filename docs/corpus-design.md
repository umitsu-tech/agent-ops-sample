# 規程コーパスの設計

社内規程の Q&A エージェントが検索する規程（`data/policies/`）の設計メモです。規程の文章は、根拠のない答えが出やすく、しかも採点しやすいように作っています。

## 会社の設定

規程は、架空の会社「株式会社ほしぞら技研」のものです。実在の会社や規程とは関係ありません。

| 項目 | 設定 |
|---|---|
| 等級 | G1〜G3（一般）、G4（主任）、M1（課長）、M2（部長）。役員は別の規程 |
| 雇用形態 | 正社員、契約社員。パートタイマーは別の規程 |
| 部署 | 人事部、総務部（情報システム課、法務・コンプライアンス担当を含む）、経理部 |
| 引き継ぎ先 | `escalate` の引き継ぎ先は人事・総務・経理の3つ。情報システムと法務は総務に含める |

## 取り込みの設定

- データソースは、規程を置くバケットの `policies/` だけを取り込みます
- チャンク分割は固定長（300 トークン、重なり 20%）です。既定と同じ値ですが、CDK で明示しています
- 表の行や附則が別のチャンクに分かれることがあります。本文と例外が別のチャンクに入り、片方だけが検索に引っかかるのも、根拠のない答えが出る原因の1つとして扱えます
- ファイル名は英語の短い名前にしています。出典の URI にそのまま出るので、答えに添えるファイル名から規程が分かるようにしています

## 改定の演習（あとで行う）

エージェントには一切触らず、規程を1本差し替えるだけで答えが変わることを示す演習です。「根拠の採点は高いまま、正解との一致だけが下がる」という形で、根拠の採点と正しさの採点の違いも見せられます。

- 差し替える文書: `ga-01-domestic-travel.md` の「宿泊費」の表と、附則
- 選んだ理由: 罠 1・2 の質問は答えが金額1つなので、採点の結果がはっきり分かれる。一般的な相場（1万円前後）とも重ならない
- 改定後の値（案）: 施行日 2026-11-01。4都市の列を G1〜G3 14,000円、G4 15,000円、M1 17,000円、M2 20,000円に、その他の地域の列を 11,000円、12,000円、14,000円、16,000円に上げる。附則に「施行日より前の宿泊は改定前の規程による」を足す
- 手順
  1. いまの規程で罠 1・2 を含む質問を流し、採点結果を `results/` に残す
  2. 改定版を `data/policies/ga-01-domestic-travel.md` に上書きし、`scripts/deploy.sh` でデプロイし直す。アップロードが更新されたあとに取り込みがもう一度かかり、終わるまで待つので、終わった時点で新しい規程が検索に出る
  3. 同じ質問を流して採点する。答えが 13,000円 から 15,000円 に変わる
- 派生（矛盾する規程）: 旧版を消さずに、改定版を別の名前（例: `ga-01-domestic-travel-2026-11.md`）で足す。新旧のチャンクが両方検索に出るので、施行日を見て答えられるかを試せる
- 改定版の置き場: 演習のときに `data/policy-revisions/` に置く。このフォルダは取り込みの対象外（アップロードされるのは `data/policies/` だけ）

## 質問集での採点

`evals/run_dataset.py` が、質問集を手元のエージェントに1問ずつ流して採点します。質問した日は 2026-09-24 に固定しています（5 と 6 は、2026-10-01 施行の改定の前後で答えが分かれるため）。

| 観点 | 測り方 |
|---|---|
| 正しさ | Jev（choice と noul）。質問、正解、答えだけを渡し、ツールの結果は渡さない |
| 根拠 | Jev。`evals/run.py` と同じ質問 |
| ツール | コード。使うべきツールをすべて呼んだか |
| 引き継ぎ | コード。引き継ぐべき質問で正しい部署に `escalate` したか、引き継がなくてよい質問で `escalate` していないか |
| 出典 | コード。根拠にすべき文書のファイル名（拡張子は省いてよい）を答えに添えたか |

2026-09-23 に、デプロイした KB で2回流した結果です。1回目のあと、レビューで 7・8・11・14 の質問と正解を直したので、2回目が今の質問集での基準になります。

| 観点 | 1回目（`dataset-20260923-110113`） | 2回目（`dataset-20260923-112821`） |
|---|---|---|
| 正しさ | 22 / 26 | 20 / 26 |
| ツール | 25 / 26 | 25 / 26 |
| ツールの引数 | （まだ測っていない） | 22 / 26 |
| 引き継ぎ | 18 / 25 | 19 / 25 |
| 出典 | 3 / 25 | 3 / 25 |
| 用件の達成 | （まだ測っていない） | 22 / 26 |
| 根拠の平均 | 0.79 | 0.72 |

- 同じ問いでも、回によって合否が入れ替わる。質問と正解を直していない問いのうち、正しさの合否が入れ替わったのは7問だった。4・15・19・22 は1回目に合格で2回目に不合格、5・9・21 は逆だった（`results/` の JSON の `correct_ok` で確認。2026-10-16 に 9 と 21 の記録漏れを足した。14 も入れ替わったが、あいだで質問と正解を直している。4 と 15 は2回目に「規程に見当たらない」と答え、答えには「人事部に引き継ぐ」と書いたが escalate は呼んでいなかった（検索で取りこぼしたのか、返ってきた規程を読み落としたのかは確かめていない）。19 は出張旅費の「2週間以内」を当てはめ、22 は勤続1年未満の条件を落とした）。1回の実行で良し悪しを決められない例として、4.4 の pass^k の話に使える
- 5 は1回目に、改定後の 30,000円 を答えた。根拠は 0.72（supported）なのに正しさは 0.06 で、根拠の採点だけでは見逃す誤りになっている
- 18 は2回とも「無料の生成 AI で議事録を要約できる」と答えた。無料版には公開情報しか入力できないという規程の文を引きながら、逆の結論を出している。正しさは 0.02 と 0.06
- 9 は「カフェは不可」と正しく答えたが、1回目の Jev は正しさ 0.38・確信度 0.0 で迷った。正解に書いた「ほしぞらラウンジ」に触れていないため。人の判定とずれる例として 4.1 で使える
- 20 は「パワハラの可能性があります」と判断に踏み込んだが、正しさは 0.58（2回目は 0.62）で agrees になった。これも人の判定とずれる例
- 引き継ぎと出典は、システムプロンプトで指示しているのにほぼ守られていない。プロンプトを直す前後を比べる題材になる
